## Media creation

Image and Video Studio creation records use a separate `business_workbench_media_studio` Domain schema v1, leaving the existing `business_workbench` XHS schema unchanged. Fixed Host Remotes expose only the five declared models and bounded session/task operations. The current adapter is Mock-only: it persists session, turn, task, artifact, and revision records through the Host storage service, reports zero provider requests, and uses opaque `mock-result://` references without storing media bytes. The isolated P2 JSON files remain untouched and are not scanned or imported by the formal Host.

## Host video packaging

The optional `videoPackaging` Host capability stores imported MP4 and PNG assets, P5-07 project JSON, and render-task records in the `business_workbench_video_packaging` Domain schema v1. Binary files live under the configured DSH home; clients address them only by Host-issued Asset IDs. Uploads use bounded chunks and finish only after size, SHA-256, file signature, and media-probe checks pass. Project saves validate Asset references and use revision checks to reject stale writes.

`listVideoPackagingAiModels` returns provider and model catalog metadata from the active Harness LLM registry without resolving credentials or sending a request. The current route does not include a dedicated Video Packaging Agent, so every returned model is marked unavailable for invocation; authentication is not inspected. The Remote does not reuse XHS `restrictedAgent` or `commentAnalysis` routes.

Rendering invokes a fixed FFmpeg executable with `shell: false`, one active task at a time, bounded duration and output size. A Host restart marks queued or running tasks interrupted and removes partial outputs; it never automatically repeats a render. Technical-test assets are rejected unless the isolated deployment explicitly enables them. The capability exposes no arbitrary filesystem paths or standalone upload server. The Client editor routes project and media operations through typed Host Remotes; its formal Desktop deployment remains separate.

The capability is disabled by default. Deployments configure `enabled`, `allowTechnicalTestAssets`, `maxVideoBytes`, `maxPngBytes`, `maxOutputBytes`, `maxProjects`, `renderTimeoutMs`, `ffmpegPath`, and `ffprobePath` on the Workbench row. The default limits are 200 MiB per video, 20 MiB per PNG, 512 MiB per output, 100 projects, and 120 seconds per render.

Host-only durable authority for Business Layer V0.1. `ctx.businessWorkbench` owns single- and four-participant Batches, execution leases, interruption recovery, frozen execution packages, exact Skill snapshots, restricted one-turn Agent execution, immutable Attempt history, text Artifacts, authoritative XHS output bundles, and deterministic XHS L1 Validation. Its narrow Host Remotes project read-only local AIHOT and Xiaohongshu data to the Client; the package adds no model-facing tool, UI, Workflow, semantic Validation, or Obsidian writer.

## Configuration

```yaml
- name: '@deepseek-ai/dsh-business-workbench'
  config:
    dshHome: /optional/isolated/dsh-home
    readRoots:
      xhs: /existing/xhs-project-root
      sharedProductTruth: /optional/existing/product-truth-root
    xhsProductionSource:
      vaultRoot: /existing/formal-vault-root
    leaseDurationMs: 30000
    commentAnalysis:
      provider: deepseek-official
      model: deepseek-v4-flash
    restrictedAgent:
      provider: deepseek-official
      model: deepseek-chat
      reasoningEffort: low
      maxTokens: 1024
      timeoutMs: 20000
```

`leaseDurationMs` is required deployment policy. `dshHome` is optional; omission follows `DSH_HOME`, then `~/.dsh`. `readRoots` is optional as a unit; when present, `xhs` is required and `sharedProductTruth` remains optional. The resolver maps `xhs/**` and `shared/product-truth/**` onto those physical roots without exposing absolute paths to callers. Package creation and input reads fail with `READ_ROOT_UNAVAILABLE` when no read policy is mounted, and a path for an unmounted logical root fails with `READ_DENIED`.

`restrictedAgent` is optional and deployment-owned. Omission keeps all Phase 1 and Phase 2 APIs available but makes Agent execution fail with `AGENT_RUNTIME_UNAVAILABLE`. Its timeout must be shorter than the execution lease. Business state uses storage domain `business_workbench`; Artifact bytes use `<dshHome>/business-workbench/v0.1/`.

`commentAnalysis` is an independent route for the approved stateless XHS comment-analysis Remote. It must name `deepseek-official` / `deepseek-v4-flash`; a missing route, another route, or an unavailable registry entry returns a content-free `COMMENT_ANALYSIS_ROUTE_NOT_CONFIGURED`, `COMMENT_ANALYSIS_ROUTE_INVALID`, or `COMMENT_ANALYSIS_ROUTE_UNAVAILABLE` error. It never reads or falls back to the Host default selection. The Web profile configures this route explicitly; other deployments must add the same configuration to their Workbench row. Analysis failures return and log only the configured provider/model, error code, failure stage, `llm.stream()` call state, tri-state provider-request status, response-observed state, HTTP status, duration, stream-event count, and response-character count. The existing analysis panel shows these fields; comment text and raw model output never enter the diagnostic.

`xhsProductionSource` is optional and requires `readRoots.xhs` to be the exact formal XHS Project below `vaultRoot`. It enables the Host-only `xhs-production-source-v1` resolver. The resolver reads the named formal entry and baseline, derives one task-card path from account/month/week/note, verifies its confirmed source-task lineage, routes `note_type` to one versioned V3.0 rule and one golden sample, and materializes one account S3 snapshot. At the System2-to-machine projection boundary, the active System2 recommendation identifier `干货推荐型（soft_plant）` maps deterministically to the canonical machine value `干货推荐型（recommendation）`; the TaskCard compiler and resolver still reject legacy or inferred machine values. It performs no directory discovery, fuzzy match, archive lookup, or fallback.

## Execution and recovery

Batch creation remains recoverable. A `single` request produces exactly one participating Job, while a `quad` request produces exactly four independent participating Jobs. Migrated V4 Batches remain `legacy-fixed4`: they retain all four historical Jobs but name the one or four Jobs with durable participation evidence. `createAttempt` creates a `pending` Attempt while the Job remains `ready`; `acquireExecutionLease` alone changes both to `running`. Renewal, release, ordinary completion, Artifact commit, and restricted Agent execution require the same owner and current Job state. Startup and explicit recovery complete abandoned XHS executions with a verified authoritative output bundle; other abandoned executions become `interrupted`. Recovery never retries model work automatically.

An execution package freezes exact input paths, hashes and sizes, Workflow version, allowed read roots/files, requested capability/Skill lists, the complete winning Skill definitions, and their origin and content hashes. Every production XHS Workflow declares a closed Skill requirement: First Pass, Revision, and Retry require exactly one account S3 snapshot, while Contract Repair requires none. Missing declarations, missing required snapshots, and unexpected snapshots on a Skill-free package fail before model I/O. Reads admit only exact frozen production inputs below `xhs/` or `shared/product-truth/`; second-pass packages may additionally name exact immutable files below the Host-mounted `business-artifacts/` root. Absolute paths, traversal, backslashes, unrelated Projects, unlisted files, non-files, symlink escape, input drift, Skill drift, and an unapproved Skill origin fail before model I/O.

The only Phase 3 action is `fixture-agent-run` for Project `xhs`. Host policy admits `restricted-agent`, `fixture-writing`, and `fixture-truth-check`; package declarations can only narrow that fixed policy. The adapter creates one fresh Harness Agent Session, replaces ambient prompt context with the frozen inputs and Skill bodies, publishes no tool schemas, installs a deny-all tool execution guard, runs the deployment-fixed model once, and disposes the live Session. It does not expose Skill discovery, filesystem, shell, Workspace, or subagent operations.

`xhs-body-prepare-v0` has explicit `fixture` and `production` routes. Its package contains exactly `taskCard`, the task-card-selected V3.0 `writingRule`, and the corresponding `goldenSample`; the account-specific S3 instruction is one exact Skill snapshot, not an input file. Each account maps to one legal Host adapter id and one formal `.agents/skills/S3-笔记写作-账号X/SKILL.md` source. The action admits no directory read, tool, discovery operation, subagent, dynamic Skill choice, or model choice.

`createXhsProductionExecutionPackage` persists content-free control, lineage, route, and S3-source evidence alongside the package. The `production` route requires that manifest, matches its account and note type, re-reads every exact source before model I/O, and accepts only the resolver-owned `project-agents / business-xhs-production-v1` S3 snapshot. Entry, baseline, source task, task card, rule, or sample drift fails with `INPUT_DRIFT`; S3 source or body drift fails with `SKILL_DRIFT`. New source bytes require a new Attempt and snapshot.

V0.1 second-pass work is additive. `createXhsReviewArtifact` records a hash-verified `PASS`, `MODIFY`, or `FAIL` review on a new single-Job revision Attempt without changing the source Job. Review version 2 identifies the exact output bundle, draft path and hash, and whether the structurally complete source is a First Pass, Revision, or successful Retry; version-1 First-Pass Reviews remain readable without migration. `xhs-body-revise-v0` admits only a `MODIFY` Review, the exact reviewed candidate, the original frozen production truth and S3 snapshot, and a lineage-derived revision number. First Pass and Retry candidates produce Revision 1, Revision 1 produces Revision 2, and Revision 2 rejects another revision with `MAX_REVISION_REACHED`. Its model instruction limits changes to `required_changes`, retains `preserve` items where compatible, and treats `quality_suggestions` as optional. Each output bundle points to the immediately reviewed candidate and Review, so the immutable chain reaches the original First Pass without overwriting any candidate.

`xhs-body-retry-v0` is distinct from revision. It admits one caller-approved retry only for empty output or deterministic `FORMAT_CONTRACT_FAIL` evidence, never for ordinary hard-contract or quality failures. The retry package omits failed draft bytes, retains the source Job and Attempt plus the closed retry reason, and uses the same frozen task identity, production inputs, account S3, output format, and validator. A successful structurally complete Retry becomes reviewable and may produce Revision 1; neither a Retry nor a Revision can enter Retry again. No retry is automatic.

`xhs-body-contract-repair-v0` is distinct from business Revision. It admits one repair per exact Candidate only when a hash-bound Review records `PASS`, the Candidate parses under the current draft format, and its matching Validation contains only deterministic failures that the closed repair vocabulary can represent. V0.1 admits title/body length, exact keyword count or title placement, declared count metadata, and topic ordering when the exact topic truth set is unchanged. Comment changes, topic-set changes, product routing, business judgments, Leo experiences, and general optimization are not caller-selectable fields and fail closed. The Skill-free package exposes only the TaskCard, Candidate, PASS Review, and matching Hard Validation; package creation, durable parsing, public verification, Host policy, and Agent preflight all enforce the same `none` requirement. Its lineage records both evidence Artifacts, failed items, repair number 1, and repaired fields. A pre-dispatch package-verification failure does not consume the one execution allowance; the abandoned Attempt remains immutable and recovery requires a new Attempt. A repaired Candidate cannot enter Repair 2 or another business Revision.

`xhs-body-length-repair-v0` is the narrower V0.2A path for a business-`PASS`, format-complete Candidate whose only deterministic failures are `titleRange` or `bodyRange`. Its Skill-free package exposes only the TaskCard, exact Candidate, bound PASS Review, and matching Hard Validation. The model may return at most three title candidates and three groups of explicit local `old_text` to `new_text` body patches; a strict JSON parser rejects complete drafts, extra fields, multiline patches, missing source text, repeated source text, and overlapping patches. The Host applies every option independently to the immutable source, regenerates character metadata with `countXhsFullCharacters`, reruns the current format and Hard Contract validators, preserves comments, topics, and every exact Review `preserve` item, and deterministically selects the passing trial with the smallest Unicode edit distance. Zero passing trials settle as `LENGTH_REPAIR_UNSATISFIED` with proposal evidence and no Candidate. One started Agent Run consumes the only repair allowance. A machine-valid result remains `CANDIDATE_READY` until a separate human Patch Approval records `APPROVE / PROMOTION_ELIGIBLE` or `REJECT / STOP`; neither decision starts another repair or writes Obsidian.

A completed Agent turn with no visible text fails as `REASONING_BUDGET_EXHAUSTED` when `max-tokens` ended a response whose reported reasoning-token count is positive, and as `EMPTY_AGENT_OUTPUT` otherwise. Diagnostic version `2` records provider, model, requested reasoning effort and output cap, Agent Run and Session ids, normalized assistant/text/reasoning/tool/final-event counts, content-field type, final-text bytes, available finish reason and token usage, duration, and failure stage without recording prompt or response bodies. The same JSON diagnostic is appended to the existing durable Agent Run `failureReason`; schema version `5` adds no diagnostic field. Missing fields stay absent when the Session event vocabulary does not carry them. Empty output never triggers a retry and reasoning blocks never become draft text. Fresh successful results also report the normalized finish reason in their non-durable execution metrics.

A successful fixture action settles one `intermediate` Artifact. A successful XHS action validates and stages `draft.md`, `draft-metadata.json`, and `provenance.json`, publishes their immutable directory, then makes one output bundle authoritative with one Job CAS. Missing files, invalid JSON, mismatched relations, hashes, sizes, or origins fail before that state update. A retry replays the single authoritative result; another successful bundle for the Attempt is rejected. Staging or published bytes left before CAS are detectable through read-only reconciliation and never become business facts automatically.

Before the model request, the Host strictly compiles the frozen formal TaskCard into `xhs-task-card-contract-v2`. The result records compiler and production identity, confirmation state, title/body ranges, note type, exact keywords and requested locations, body-structure labels, product module, comment counts, the exact ordered topic values, and explicit prohibitions. Missing compiler identity, legacy note types, duplicate fields or topics, a topic count that differs from the listed values, absent keyword policy, and conflicting SEO keyword declarations fail closed. For production sources, both the upstream task and compiled TaskCard must be confirmed and must contain the same ten unique topic values in the same order before an execution package can be created. `SEO高亮词：无` is the sole explicit representation of an empty exact-keyword requirement; omission is never treated as empty. A concise `【本篇执行硬合同】` checklist is appended to the final user instruction and repeats only the compiled rules, including every required hashtag.

After the response, `xhs-hard-contract-l1-v3` first requires `xhs-draft-markdown-v1`: one leading H1 title, the combined model-declared count line immediately below it, and ordered `置顶评论`, `非置顶评论`, and `关联话题` H2 sections. A format failure records `FORMAT_CONTRACT_FAIL`, null actual counts, and `NOT_EVALUATED` checks instead of guessing content ranges. Once parsing succeeds, the validator counts title and body Unicode code points independently of model-declared counts, records exact keyword offsets, checks required title keywords, total keyword minima, comment counts, and compares the final ordered hashtag strings exactly with the TaskCard list. Missing, unexpected, duplicate, reordered, or eleventh topics return `HARD_CONTRACT_FAIL` with `expected_topics`, `actual_topics`, `missing_topics`, and `unexpected_topics`; no alias, normalization, or semantic match is accepted. Opening/middle/ending keyword locations, body-structure meaning, product-module meaning, and prose prohibitions remain deferred evidence because no machine boundary is defined. Validation result version 4 records these distinctions inside the unchanged version-5 Business Artifact. The validator never edits the draft or calls a model. The output bundle and one immutable `validation` Artifact become authoritative in the same Job CAS, so restart and idempotent replay retain the raw First-Pass draft and its deterministic result together.

`replayXhsHistoricalDraft` is a read-only evidence path for pre-format-contract drafts. It preserves their format failure and emits hard-rule evidence only when one known historical layout identifies the title, body, comments, and topics without ambiguity; it never makes the old layout valid for a future production run.

After a human approves a final body, `buildXhsCoverHandoffArtifact` creates a separate immutable `xhs-cover-handoff-v0.1` Artifact without writing back to the Obsidian body. It binds the body path, SHA-256, finalization state, `note_type`, complete `title_pair_contract`, per-field sources, human decision source, creation time, and task lineage. A missing field, body-hash drift, final-title conflict, or primary number absent from the body fails before S15. `buildXhsSearchSolutionCoverPlan` fixes the search-solution route to `V2_1_Swiss_Purple_QingYa`, the P1-P8 template order, shared Swiss title capacities, `SENSE / JUDGE / ACT` nodes, and the sole P5 image slot without calling a model or image service.

XHS policy `xhs-body-prepare-policy-v2-text` accepts Markdown final text, not a model-authored JSON envelope. The Host removes at most one initial BOM, preserves all other draft bytes, and encodes the strict internal `{draft: string}` envelope with `JSON.stringify`. Leading JSON containers or code fences, empty text, embedded BOM/NUL, oversized drafts, and reported `max-tokens` termination fail closed. No extraction, JSON repair, fence stripping, or second model call occurs. `XHS_BODY_OUTPUT_INVALID` carries content-free `xhsOutputDiagnostics` with classification, stage, UTF-8 byte count, hash, and observed finish reason; the existing durable `failureReason` retains that JSON without changing V5. Missing finish evidence is not inferred.

The storage domain has schema version `5`. Each Batch records `single`, `quad`, or migrated `legacy-fixed4` participation and explicit participating Job ids. Each Attempt carries an optional production-source manifest and a nullable authoritative output bundle, and completed Agent Runs reference exactly one Artifact or output bundle. Versions 0 through 4 and every unknown version reject at ordinary open without mutation. The package provides one explicit, hash-gated, operator-run V4-to-V5 JSON migration; it is never invoked at Runtime startup.

## Model Experience

### Restricted fixture Agent request

#### What the model sees

Every restricted action provides one complete system prompt containing only Host-fixed action instructions and admitted Skill snapshots, followed by one user message containing action metadata and frozen input bytes. Draft-producing XHS actions append the TaskCard-derived execution checklist and fixed `xhs-draft-markdown-v1` structure. Revision additionally receives the immutable currently reviewed candidate and its Review; Retry never receives failed draft bytes. Contract Repair receives the Candidate, PASS Review, and matching Hard Validation but no Skill, writing rule, or golden sample. Length Repair receives the same four frozen evidence inputs but returns only a bounded JSON patch proposal; it never returns a draft or authors character metadata. Other draft actions return one H1 title, the combined declared-count line, body, ordered comment sections, and the topic section as plain Markdown without JSON, a code fence, or an outer report. The Host authors metadata, provenance, and L1 Validation; native provider JSON mode is not requested. The Session receives no preset, prior messages, runtime context, discovery result, or callable tool. Other APIs produce no model request.

#### Token effect

One request contains the complete selected Skill bodies and input files plus fixed metadata. Cost therefore grows with the frozen package bytes; the temporary Session adds no later turn.

#### KV Cache effect

Each invocation uses a fresh Session and a complete prompt assembled from immutable package content. Requests with identical package and deployment policy may share a provider-side prefix, but this package keeps no application cache and makes no cache guarantee.

### Stateless XHS comment-demand analysis

The XHS comment-demand path is a scoped exception to the Session-reconstructability rule. It calls the existing `ctx.llm.stream()` route directly without an Agent, Session, `sessionId`, tools, or `SessionPersistence`, explicitly setting `reasoningEffort` to `off` and `maxTokens` to `4096` for each request. This prevents deployment defaults from spending the shared output budget on reasoning while keeping a finite completion cap. The prompt and Host validation cap insights at three per category, fifteen total, and 120 characters per insight. The request includes only note title, note text, and at most ten non-empty comment texts with temporary evidence refs. Raw prompt and completion stay in request memory and are discarded after Host validation. Only validated insights enter the bounded in-memory cache. The provider receives comment text; “not written to Harness Session” does not mean “not sent outside this device.”

The Host collects `text-delta` chunks and uses a completed text `block-end` only when that block emitted no non-empty deltas. Reasoning, tool, usage, and finish chunks never become model response text. A normal completion without text returns `EMPTY_RESPONSE`; a Provider finish error with that code returns `PROVIDER_EMPTY_RESPONSE`, a max-token finish returns `PROVIDER_MAX_TOKENS`, oversized output returns `ANALYSIS_RESPONSE_TOO_LARGE`, and non-empty unparseable text returns `ANALYSIS_PARSE_ERROR`.

### AIHOT evidence analysis Session

The internal `AihotAnalysisRunner` sends one bounded A3-03 Evidence Pack through `HarnessRestrictedAgentRuntime`. It creates a separate persisted Agent Session, excludes ambient Session history and tools, and requires `SessionPersistence`; the standard checkpoint policy writes the complete request before Provider dispatch. The request header records the exact system instructions and model route, the user message contains the serialized Evidence Pack snapshot, and the Session records the response and turn outcome. Cancellation uses `Agent.cancel`; timeouts use the same Agent cancellation path. The A3-03 validator checks the response before the runner returns it. A stored response can be revalidated from the Session log; the derived validation verdict is not a separate Session event. The runner has no Remote, UI, automatic caller, or real-provider verification.

#### Token effect

One configured Provider request receives one Evidence Pack capped at 32,000 UTF-8 bytes plus a bounded instruction envelope. A real call may incur the configured Provider's ordinary usage charges; tests use a fixture adapter.

#### KV Cache effect

Each run uses a fresh Session with no application-level prompt cache or reuse guarantee.

## Known Limitations and Deferred Work

- **Single Runtime writer** — one Runtime may mount this domain for one `DSH_HOME`; no cross-process lock is added.
- **One explicit migration only** — the operator-run V4-to-V5 JSON migration is the sole supported migration; schemas 0 through 3 and unknown versions remain incompatible.
- **Closed Batch sizes** — new Batches are exactly `single` or `quad`; arbitrary N-Job scheduling is unsupported, and `legacy-fixed4` is migration-only.
- **No Human Gate UI** — Review Artifacts and at most two bounded revision executions exist, but review capture has no UI and approved-asset finalization and promotion do not exist.
- **No automatic retry** — one structural retry may be prepared only through explicit Host APIs; interruption and other provider failures remain caller-controlled.
- **No orphan cleanup** — reconciliation is read-only.
- **AIHOT analysis has no product caller** — the internal runner requires a configured restricted-Agent model and Session persistence, but exposes no Remote or UI and has not been verified against a real Provider.
- **No formal Desktop deployment** — the Video Packaging Client and Host integration has only been exercised in an isolated S3 profile; the formal Desktop and its DSH home remain unchanged.
